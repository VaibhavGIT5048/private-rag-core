1. PROJECT OVERVIEW — WHAT, WHY, USE CASES
================================================================================

1.1 WHAT WE ARE BUILDING
--------------------------------------------------------------------------------
Grounded-RAG is a production-grade, multi-tenant Retrieval-Augmented Generation
platform. A signed-in user uploads a document — a PDF, a Word file, a
spreadsheet, a scanned image — and can then ask natural-language questions about
it. The system answers using ONLY the content of that document, and every claim
in the answer carries a clickable citation pointing back to the exact source
file and page it came from.

The emphasis is on the word GROUNDED. A general-purpose chatbot answers from
whatever it absorbed during training, which means it will confidently invent a
figure that does not exist in your document. This system is architecturally
prevented from doing that: the model is only ever shown text retrieved from the
user's own document, it is instructed to refuse when the document does not
support an answer, and its output is validated before it is returned.

1.2 WHY WE ARE BUILDING IT
--------------------------------------------------------------------------------
Three problems motivated this, in order of importance:

(a) THE HALLUCINATION PROBLEM.
    Large language models produce fluent, plausible, confident text regardless
    of whether they know the answer. For casual use that is tolerable. For a
    contract, a research paper, a compliance report, or a medical document, a
    fabricated number is worse than no answer at all, because it is
    indistinguishable from a real one. Retrieval-augmented generation addresses
    this by changing the question the model is asked. Instead of "what is the
    carbon reduction target?" (which invites recall, and therefore invention),
    the model is asked "given exactly this text, what is the carbon reduction
    target?" (which invites reading). Citations then make the answer auditable:
    the user does not have to trust the model, they can check it in one click.

(b) THE DOCUMENT SCALE PROBLEM.
    Modern models have large context windows, and it is tempting to conclude
    that RAG is unnecessary — just paste the whole document in. This fails for
    three separate reasons. First, cost: input tokens are billed, and pushing a
    200-page document through the model on every question is enormously more
    expensive than pushing the four relevant paragraphs. Second, latency: a
    large prompt is slower to process. Third, and most importantly, quality:
    the well-documented "lost in the middle" effect means retrieval accuracy
    degrades for information buried in the centre of a very long context. A
    focused, relevant context outperforms an exhaustive one.

(c) THE PRIVACY AND OWNERSHIP PROBLEM.
    Uploading a confidential document to a third-party chatbot means handing
    that content to a company whose data-retention policy you do not control.
    This system is deliberately built so the operator controls the whole path.
    Embeddings — the step that reads every single word of every document — run
    on a self-hosted model inside our own container, so for that stage the raw
    text never leaves the infrastructure at all. Generation runs on Azure
    OpenAI billed to our own subscription. And a user who wants to eliminate
    even that can supply their own OpenAI key, in which case generation is
    billed to them and routed to their account.

1.3 USE CASES
--------------------------------------------------------------------------------
Realistic applications, with the reason RAG specifically fits:

  * LEGAL AND CONTRACT REVIEW — "What is the termination notice period?" The
    citation matters more than the answer; a lawyer needs the clause, not a
    summary.

  * ACADEMIC RESEARCH — Querying dense papers where the answer is one sentence
    inside forty pages. Structure-aware chunking keeps section headings
    attached, so "what did the methodology section say" is answerable.

  * FINANCIAL AND ANNUAL REPORTS — Numbers scattered across tables and
    appendices. Hybrid retrieval matters here: BM25 catches exact figures and
    identifiers that a purely semantic search would blur.

  * COMPLIANCE AND POLICY — "Does this policy mention data retention?" A
    refusal ("the document does not state this") is a genuinely valuable
    answer, and this system is built to give it rather than guess.

  * TECHNICAL DOCUMENTATION AND ONBOARDING — Internal manuals where new staff
    do not yet know the vocabulary to search keywords effectively; semantic
    search covers the gap.

  * SCANNED AND IMAGE-BASED ARCHIVES — Older material with no text layer at
    all, handled by the OCR tier of the parser router.

3.1 THE RAG PIPELINE, STAGE BY STAGE
--------------------------------------------------------------------------------

INGEST PATH (POST /ingest, or POST /ingest/async for large files):

  1. AUTHENTICATE — JWT decoded, owner_id extracted. No anonymous ingest.
  2. RATE LIMIT — 10 ingests/hour/user by default (INGEST_RATE_LIMIT).
  3. PARSE — the parser router selects an extraction backend by file extension
     and escalates to a paid OCR tier only if the free tier's output fails a
     quality check (see 3.6).
  4. CHUNK — structure-aware splitting on the document's own headings (see 3.2).
  5. QUALITY GATE — each chunk scored out of 7 on heuristics (length, sentence
     completeness, alphanumeric ratio, section membership). Note carefully:
     this does NOT drop chunks. Every non-empty chunk is indexed. The score
     applies a 0.7 ranking multiplier to weak chunks at retrieval time. The
     response field was historically named `dropped_chunks`, which was
     misleading, and is now reported as penalised.
  6. EMBED — all chunks embedded in one batched call to bge-m3.
  7. INDEX — vectors upserted into the shared Qdrant collection with
     document_id and owner_id in the payload; a BM25 index is pickled to
     data/documents/{owner_id}/{document_id}/bm25.pkl.
  8. RECORD — a row in the SQLite `documents` table.

QUERY PATH (POST /query):

  1. AUTHENTICATE + RATE LIMIT — 60 queries/hour/user by default.
  2. LOAD ARTIFACTS — BM25 index + chunks for that document, via the two-tier
     cache (in-process LRU → Redis → Azure Files).
  3. SANITISE — NFKC Unicode normalisation, control/zero-width/bidi character
     stripping, length cap, injection pattern detection (see section 7).
  4. QUERY REWRITE — if the conversation has history, one small LLM call
     resolves references against the last few turns, so "what about the second
     one" becomes a self-contained query. Skipped entirely on the first
     question, and skipped if the question looks like an injection attempt
     (rewriting an attack would launder it past the filters designed to catch
     it).
  5. HYBRID RETRIEVE — dense vector search in Qdrant (filtered to this
     document and owner) run alongside sparse BM25 keyword search over the
     same document's chunks.
  6. FUSE — Reciprocal Rank Fusion combines the two ranked lists.
  7. PENALISE — quality-gate multiplier applied.
  8. RERANK — FlashRank cross-encoder reorders the candidate pool and takes
     top-K.
  9. EXPAND — each surviving chunk pulls in its immediate neighbours (window
     ±1) so an answer is not cut off mid-sentence at a chunk boundary.
  10. BUDGET — chunks are assembled into a context blob under a token budget
      (MAX_CONTEXT_TOKENS, default 6000, counted with tiktoken); the
      lowest-scoring chunks are dropped first if it would overflow.
  11. WRAP — the context is enclosed in explicit untrusted-data markers.
  12. GENERATE — gpt-5-mini via Azure OpenAI, with the strict grounding system
      prompt.
  13. VALIDATE OUTPUT — the response is checked for leaked system-prompt text
      or infrastructure identifiers before it is returned.
  14. PERSIST — question, answer, and sources JSON written to `chat_turns`.
  15. LOG TIMINGS — per-stage milliseconds emitted as structured JSON.


3.2 CHUNKING — THREE STRATEGIES AND WHY ONE WON
--------------------------------------------------------------------------------
Chunking is the highest-leverage and most underrated decision in a RAG system.
Too small and you sever the context a sentence needs; too large and you dilute
the embedding so retrieval stops discriminating.

We implemented and measured three strategies on the same 44-page WEF PDF, with
self-hosted bge-m3 on CPU:

  STRATEGY          TIME     CHUNKS   PASSED GATE
  ---------------------------------------------------------
  Semantic          7m 28s   107      68  (64%)
  Recursive         1m 31s   169      135 (80%)
  Structure-aware   ~1m 33s  189      163 (86%)

SEMANTIC CHUNKING (removed). LangChain's SemanticChunker embeds every sentence
and splits where consecutive sentence embeddings diverge past a threshold. It
sounds principled. In practice it cost roughly six of those seven and a half
minutes, because it runs a complete second embedding pass over the document on
top of the one that actually indexes the chunks. Worse, 7m28s exceeds Azure
Container Apps' ~240-second ingress timeout, so an ingest that completed fine
locally would be severed mid-request in production. It was deleted outright —
not merely disabled behind a flag — along with the `SEMANTIC_CHUNKING`
environment variable, the langchain adapter that existed only to feed it, and
the `langchain-experimental` dependency. It cost 5x the ingest time for a
benefit that was never demonstrated.

RECURSIVE CHARACTER SPLITTING (retained as fallback). Splits on paragraph, then
sentence, then word boundaries to hit a target character count. Fast, dumb,
reliable.

STRUCTURE-AWARE CHUNKING (current default, CHUNKING_STRATEGY=structure). Splits
on the document's own headings. It costs no model call whatsoever, so it
removes the semantic pass rather than merely speeding it up. Headings are
detected by markdown `#` markers first, then numbered sections, then ALL CAPS
lines, then Title Case, with lines rejected if they exceed 90 characters or end
in sentence punctuation. Each chunk carries a `section` field in its metadata,
which is useful for citations as well as retrieval. Oversized sections fall
back to the recursive splitter within that section. Page metadata is preserved
throughout, because page numbers drive citations.

AN IMPORTANT CAVEAT WE DOCUMENTED RATHER THAN HID: the 64%-vs-86% quality-gate
pass rates above are partly an artefact. The gate awards 2 of its 7 points for
landing in a fixed 50–300 token window, which uniform recursive chunks hit by
construction and variable-size semantic chunks miss. The gate is calibrated for
fixed-size chunking. The honest comparison is the retrieval quality test, which
structure-aware also won.


3.3 EMBEDDINGS — THE SELF-HOSTED DECISION
--------------------------------------------------------------------------------
An embedding model converts text into a vector of numbers such that texts with
similar meaning land near each other in that space. This is what makes semantic
search possible: the question is embedded, and the nearest chunk vectors are
retrieved, even when they share no keywords with the question.

MODEL: BAAI/bge-m3, open-weight (MIT licence), self-hosted in-process.

WHY NOT OpenAI text-embedding-3-small:
  * Quality: bge-m3 scores 63.0 MTEB vs 62.3 — comparable or better.
  * Context: 8192 tokens vs 512 — a 16x larger effective range, which matters
    for long chunks.
  * Multilingual and hybrid dense/sparse/multi-vector output, natively.
  * Cost: $0 marginal. It rides the same scale-to-zero container billing as
    everything else instead of adding a per-token metered API call. Embedding
    is the one stage that reads EVERY word of EVERY document, so it is exactly
    the stage where per-token pricing hurts most.
  * Privacy: the rawest form of the user's text never leaves our infrastructure
    for this stage.

WHY NOT larger BGE variants: bge-en-icl and bge-multilingual-gemma2 are 7B and
9B parameters. CPU inference would be seconds per call, and GPU-backed managed
compute costs hundreds of dollars a month at a fixed rate — the same trap that
ruled out Phi-4 (see 3.5).

DIMENSION: 1024 (the Qdrant collection's vector_size was migrated from 1536 to
1024 as part of the same rebuild that added multi-document support).

BATCHING: measured on 60 real chunks across 10 cores — batch size 8 gave 36.2s,
16 gave 40.9s, 32 gave 48.6s. Smaller wins, because bge-m3 accepts long
sequences and a large batch pads every short text up to the longest one in it.
Default is 8.

INT8 ONNX QUANTIZATION (specified, implemented behind a flag, NOT yet default).
Converting to INT8 ONNX would cut the model from 2.3GB to roughly 570MB at a
measured 0.989 mean cosine similarity to full precision — negligible retrieval
loss. It is behind EMBEDDING_BACKEND=onnx rather than on by default for a
specific reason: the meaningful INT8 speedup comes from AVX512-VNNI kernels,
which are x86-only. The development machine is arm64 (Apple Silicon), so a
local benchmark would actively mislead. It must be validated on staging, which
is x86, before becoming the default.


3.4 RETRIEVAL — HYBRID SEARCH, FUSION, RERANKING
--------------------------------------------------------------------------------
Retrieval runs two independent searches and combines them, because they fail in
opposite directions.

DENSE (semantic) search via Qdrant finds text that MEANS the same thing as the
query even with no shared words. It is weak on exact identifiers — a part
number, a specific figure, an acronym — because embeddings blur precise tokens.

SPARSE (keyword) search via BM25 finds exact term matches and is excellent at
identifiers and rare words. It is blind to synonyms and paraphrase.

RECIPROCAL RANK FUSION merges the two ranked lists using 1/(k + rank) summed
across lists. It is deliberately rank-based rather than score-based, because
the two systems' scores are not comparable quantities — a BM25 score and a
cosine similarity live on different scales, and naively normalising them
introduces bias. Note for anyone reading the source: RRF scores are tiny
(~0.04) and are NOT similarities. The UI's score bars normalise against the
maximum in the current result set rather than treating the value as a 0–1
fraction, which would render every bar nearly empty.

RERANKING with FlashRank. The fused candidate pool goes through a cross-encoder
reranker. Where the embedding model encodes query and document separately (fast,
but it never actually compares them directly), a cross-encoder reads the query
and the candidate TOGETHER and scores relevance. It is far more accurate and far
slower, which is exactly why it runs on a small candidate pool rather than the
whole corpus. This is the standard retrieve-then-rerank pattern.

NEIGHBOUR EXPANSION. Each surviving chunk pulls in its adjacent chunks (window
±1). Chunk boundaries are arbitrary relative to meaning, and an answer that
begins in one chunk frequently completes in the next.

FILTERED SEARCH AND THE ef_search CAVEAT. Every query filters on document_id and
owner_id. Qdrant's HNSW index (default m=16, ef_construct=100) loses recall
under filtering, because the graph traversal keeps hitting nodes that the filter
excludes. `ef_search` is raised explicitly to compensate.


3.5 GENERATION — THE MODEL SELECTION SAGA
--------------------------------------------------------------------------------
This took four dead ends before landing, and every one is worth recording
because they will recur for anyone repeating this on a student subscription.

ATTEMPT 1 — Phi-4. The original pick, chosen as a small efficient open model.
On this subscription it is only offered via Global Managed Compute — GPU
templates (MI300X/A100/H100) with no serverless option. Managed compute cannot
scale to zero. Confirmed cost: roughly $2,681 to $70,000+ per month depending on
GPU tier, billed whether or not anyone uses it. Ruled out completely.

ATTEMPT 2 — gpt-4.1-mini. Benchmarks well (+5.5 MMLU, +20 instruction-following
against gpt-4o-mini, 1M token context). Two blockers: it retires 14 October
2026, roughly two months out, and Global Standard deployment was not offered for
it in Central India at all — only Global Provisioned Throughput, a
reserved-capacity billing model, which then failed on insufficient quota anyway.

ATTEMPT 3 — gpt-4o-mini. Confirmed already deprecated; the deployment dialog
blocks it outright. Note that deprecated models remain visible in catalog
LISTINGS even once undeployable, which makes the catalog misleading.

ROOT CAUSE FOUND. The subscription carries a system-assigned Azure Policy
(`sys.regionrestriction`) capping deployable regions to exactly five:
austriaeast, uaenorth, malaysiawest, centralindia, eastasia. Of those,
austriaeast and malaysiawest do not have the Cognitive Services resource
provider registered at all, and centralindia and eastasia both carry the same
stale, mostly-deprecated 9-model catalog with no gpt-5 family whatsoever.

ATTEMPT 4 — SUCCESS. uaenorth turned out to carry a completely different,
current catalog — verified with `az cognitiveservices model list -l uaenorth` —
including the full gpt-5 and gpt-5.1–5.6 families, plus Claude, Grok, DeepSeek,
Mistral and Cohere.

FINAL: gpt-5-mini, deployed Global Standard in UAE North.
  * $0.125 per 1M input tokens, $1.00 per 1M output — cheaper than
    gpt-4.1-mini's $0.40/$1.60.
  * On no retirement timeline, and Microsoft's own migration guidance for the
    retiring gpt-4.1/gpt-4o families points at the gpt-5 family.

ACCEPTED CONSEQUENCE: the chat deployment lives in a different region (UAE
North) from everything else (Central India). This is fine — it is an interactive
HTTPS call, not something requiring co-location, and Middle East to South Asia
is a short hop, plausibly better than a US or EU region would have been.

DEFERRED OPTION: claude-sonnet-5 is also available serverless in the UAE North
catalog and has a strong reputation for grounding and instruction-following
fidelity, which is precisely what this pipeline's strict-citation requirement
needs. At roughly 13–19x gpt-5-mini's per-token cost it was not worth blocking
deployment on, but it is the obvious candidate for a quality comparison once
usage justifies it.

BYO KEY PATH: a user may supply their own OpenAI API key in the UI. It is stored
only in their browser, sent as a per-request header, and never persisted
server-side. It swaps the CHAT model only. Embeddings always use the default
provider, deliberately: a document's vectors are permanently tied to the model
and dimension that indexed them, and the collection has one fixed vector size,
so allowing embeddings to swap per-request would silently corrupt retrieval.


3.6 THE PARSER ROUTER (MULTI-VENDOR OCR)
--------------------------------------------------------------------------------
A tiered escalation system that tries free local extraction first and escalates
to a paid vendor only when the free result fails a quality check.

  EXTENSION        PRIMARY                    FALLBACK
  ---------------------------------------------------------------------
  .pdf             local (pypdf)              Azure Doc Intelligence Layout
  .docx            local                      Azure Doc Intelligence Layout
  .pptx            Azure DI Layout            —
  .xlsx            Azure DI Layout            —
  .csv             local (stdlib csv)         — (never needs a service)
  .jpg/.jpeg       Mistral OCR                Azure DI Read
  .png             local                      Azure DI Read
  .webp            Mistral OCR                Mistral retry only

EXTRACTION QUALITY SCORING combines character density AND printable-character
ratio. Either check alone misses a real failure mode: density alone passes a
garbled OCR result that produced plenty of junk characters, and printable ratio
alone passes a nearly-empty scan that produced three clean words.

TWO FORMAT-SPECIFIC NOTES:
  * .csv never needs an extraction service. It is already flat machine-readable
    text; routing it through OCR would be slower, cost money, and risk
    misreading values.
  * .webp has NO Azure fallback in any capacity — confirmed absent from both
    Document Intelligence's and Content Understanding's supported-format lists.
    Its only path is a Mistral retry.

COST CONTROL: `prebuilt-read` and `prebuilt-layout` are called directly.
`prebuilt-documentSearch` and any analyzer with figure-analysis or field
extraction enabled are deliberately avoided, because those invoke an LLM and
cost substantially more (Microsoft's own worked example: $13.20 vs $5.00 per
1,000 pages) for a capability this pipeline does not use.

`is_available()` is used as a ROUTING SIGNAL rather than raising an exception,
so an unconfigured vendor is skipped cleanly and the file degrades to the local
tier instead of failing the ingest.


3.7 ASYNC INGEST JOBS
--------------------------------------------------------------------------------
POST /ingest/async returns HTTP 202 with a job id immediately; GET
/ingest/jobs/{job_id} polls status. This exists because Azure Container Apps
severs a request at roughly 240 seconds. A large document plus per-file OCR
network calls can exceed that, and without the async path large-document ingest
is permanently deployment-blocked no matter how fast the chunker is.


3.8 BACKEND CHALLENGES AND HOW THEY WERE SOLVED
--------------------------------------------------------------------------------

CHALLENGE 1 — EVERY INGEST WIPED THE ENTIRE DATABASE.
`build_hybrid_indices()` called `client.recreate_collection(...)`, which drops
and recreates the Qdrant collection. Uploading a second document silently
destroyed the first. Fixed to create-if-missing plus upsert.

CHALLENGE 2 — CHUNK IDs COLLIDED ACROSS DOCUMENTS.
chunk_id reset to 0..N on every ingest and was used directly as the Qdrant point
ID. Document B's chunk 5 overwrote document A's chunk 5. Fixed with
uuid5(document_id, chunk_index) — deterministic, stable, and globally unique.

CHALLENGE 3 — ONE GLOBAL BM25 FILE FOR THE ENTIRE DEPLOYMENT.
bm25_data.pkl was a single file holding one index for everything. Now written
per document at data/documents/{owner_id}/{document_id}/bm25.pkl.

CHALLENGE 4 — ONE SLOW REQUEST FROZE THE WHOLE SERVER.
Routes were declared `async def` but called synchronous, CPU-bound
`RAGService.ingest`/`.answer` directly. In an async framework that blocks the
event loop, so a single ingest froze every other request including /health.
Fixed by wrapping those calls in `await asyncio.to_thread(...)` — the smallest
change that fixes it, without an async rewrite of the RAG internals.

CHALLENGE 5 — THREE COPIES OF A 2.3GB MODEL LOADED SIMULTANEOUSLY.
`BgeEmbeddingProvider._load()` had no lock. Ingest embeds via a
ThreadPoolExecutor, so all three workers saw `_model is None` at the same
moment and each loaded its own full copy. Measured cost on a 44-page PDF: ~5m00s
versus ~1m30s once serialised. Fixed with double-checked locking, publishing
`self._model` only after the model is fully constructed so no thread can observe
a half-initialised object.

CHALLENGE 6 — PARALLELISM THAT MADE THINGS SLOWER.
The embedding path fanned work out across a ThreadPoolExecutor. Measured on 60
real chunks and 10 cores: 45.7s with the 3-way fan-out versus 36.2s with a
single `encode()` call. Two reasons — torch already parallelises across every
core, so the fan-out oversubscribed the CPU; and sentence-transformers sorts by
length internally to minimise padding, which external batch-splitting defeats.
The fan-out was deleted rather than tuned.

CHALLENGE 7 — EVERY QUERY RETURNED HTTP 500 (QDRANT PAYLOAD INDEXES).
Symptom: ingest succeeded, every subsequent question failed. Qdrant rejected the
filtered search outright:
    Bad request: Index required but not found for "document_id"
    of one of the following types: [keyword, uuid]
Multi-document support added a document_id/owner_id FILTER but never created the
payload INDEXES Qdrant requires to filter on those keys. Fixed by creating the
indexes, and crucially by running `_ensure_payload_indexes` on every ingest
rather than only at collection creation — collections built before the filters
existed have to pick the indexes up too, and creating an existing index is a
no-op.

CHALLENGE 8 — A 500 THAT LOOKED LIKE A NETWORK OUTAGE.
The above failure surfaced in the browser as "Could not reach the backend" with
no request id, which sent debugging in completely the wrong direction. Cause:
unhandled exceptions reached Starlette's ServerErrorMiddleware, which sits
OUTSIDE every user middleware including CORS. The 500 therefore carried no
Access-Control-Allow-Origin header, so the browser blocked it before the client
could read the status. Fixed by catching in the request-context middleware and
registering CORS last so it wraps the error response. Verified empirically
against real Starlette: CORS-first yields no ACAO header on a 500, CORS-last
yields it.

CHALLENGE 9 — SQLITE ON AZURE FILES (SMB) CRASH-LOOP.
SQLite's WAL journal mode requires shared memory and byte-range locking, which
SMB-backed Azure Files does not provide reliably. Solved with the `nobrl` mount
option and by not depending on WAL semantics.

CHALLENGE 10 — CONTAINER CRASH-LOOP FROM A MISSING FILE SHARE.
New revisions failed with:
    VolumeMountFailure ... mount error(2): No such file or directory
The Container App's volume config referenced a share named `rag-data-staging`
that had never actually been created — only `rag-data` existed. The share
creation step in configure_staging.sh swallowed both stdout and stderr and
printed "(share already exists)" on ANY non-zero exit, so a genuine failure was
indistinguishable from success. Two lessons: a script that cannot fail loudly
cannot be trusted, and Container Apps will happily leave a broken revision
holding 100% of traffic while a healthy older revision sits at 0%.

CHALLENGE 11 — A REVISION SERVING 100% OF TRAFFIC WITH ZERO REPLICAS.
Diagnosing the above surfaced a genuinely counter-intuitive property of Azure
Container Apps: traffic weight and health state are INDEPENDENT. `az containerapp
revision list` showed revision --0000007 holding 100% traffic while Unhealthy
with 0 replicas, and an older healthy revision at 0% traffic. Live requests were
being routed to a revision that could not serve them. Always check both columns.

CHALLENGE 12 — A TRUNCATED SECRET FROM AN UNQUOTED SEMICOLON.
The Azure Communication Services connection string contains `;`. Sourcing the
env file without quoting truncated it at the first semicolon, so OTP email
failed with an opaque "Invalid connection string" error at runtime rather than
at configuration time.

CHALLENGE 13 — MODEL WEIGHTS RE-DOWNLOADED ON EVERY COLD START.
The bge-m3 weights (~2.3GB) were never baked into the Docker image. They
downloaded from HuggingFace on first use into /home/appuser/.cache/huggingface,
which is container-local ephemeral storage — the Azure Files volume only covers
/home/appuser/app/data. With minReplicas 0, every scale-to-zero discarded them,
so EVERY cold start re-downloaded multiple gigabytes before the first question
could be answered. This dominated both wake time and first-query latency.
Fixed by baking the weights into the image (see 9.2 for the caching design).

CHALLENGE 14 — A SHA-PINNED MODEL DOWNLOAD THAT COULD NOT BE LOADED OFFLINE.
`snapshot_download` pinned to a commit sha writes `snapshots/<sha>/` but never
writes `refs/main`. Loading "BAAI/bge-m3" by repo id resolves main → sha through
that ref, so with the network disabled there was nothing to resolve and
transformers reported the files as simply not cached — despite them being
present in the image. Rather than hand-writing the missing ref, the fix loads
from a plain filesystem directory (`local_dir`), bypassing hub resolution
entirely. This was caught by a deliberate build-time offline-load check, which
is the only reason it did not ship as a silent regression to re-downloading.

CHALLENGE 15 — A GIT HISTORY INCIDENT.
Two commits disappeared from `develop`'s ancestry. Root cause identified
precisely from the reflog: an orphan commit (no parent) followed by a
`git merge -s ours`, which keeps the current branch's tree entirely while still
recording the other commit as a parent — so the commits appeared merged in
history while their content was absent from the tree. Content loss was ruled out
with `git diff --stat <commit> -- <paths>` returning empty, proving the files
were byte-identical in the current tree.

4.1 STACK AND DESIGN SYSTEM
--------------------------------------------------------------------------------
  * Next.js 15 (App Router), exported as a fully STATIC site. There is no Node
    server in production — the output is HTML/CSS/JS on GitHub Pages, which is
    free, fast, and has no attack surface of its own.

  * Tailwind CSS 3.4 for layout utilities, layered over a CSS custom-property

  * framer-motion for motion, with a global motion preference (Full / Reduced /

  * lucide-react for icons.
  * react-markdown for answer rendering.

THE DESIGN SYSTEM. Colour, border, radius and blur are CSS custom properties
(--ink, --accent, --brd, --panel, --chip-bg, --r-sm, --brd-w, --blur) rather
than hardcoded values. Two themes ship — "Light" and "Dark" — and
because every component reads the tokens rather than literals, switching themes
is a variable swap with no component changes. This is also what makes the app
safe to restyle: a change to the palette cannot miss a component.

ON "CLAUDE DESIGN" / AI-ASSISTED DEVELOPMENT. This project was built with heavy
AI-assisted engineering (Claude Code) as a working partner rather than an
autocomplete. Practically, that shaped three things worth recording:
  (a) Design decisions were driven by measurement, not vibes — the chunking
      strategy, the batch size, the parallelism removal, and the CORS ordering
      were all settled with an experiment rather than an argument.
  (b) Every non-obvious decision is documented in a code comment explaining
      WHY, not what. The codebase is unusually heavily commented at the
      decision points and deliberately sparse elsewhere.
  (c) Bugs were traced to root cause rather than patched at the symptom — the
      CORS/500 interaction and the grid overflow arithmetic below are examples
      where the visible symptom pointed somewhere completely different from the
      actual cause.

4.3 FRONTEND CHALLENGES AND HOW THEY WERE SOLVED
--------------------------------------------------------------------------------

CHALLENGE 1 — ANSWERS RENDERED AS RAW MARKDOWN SYMBOLS.
`**Education**` displayed literally instead of bold. The answer string was being
dumped into a plain span with no Markdown parser. The naive fix — split the
string around citations and render the pieces — is what the code already did,
and it is the reason a Markdown parser could not simply be dropped in: splitting
breaks any list item or bold run a citation sits inside, handing the parser two
malformed fragments. Solution: rewrite each `[Source: x | Page: y]` marker into
a Markdown LINK on a fake `cite:` scheme BEFORE parsing, so one parse covers the
whole answer coherently, then intercept those links in the renderer and swap
them back for interactive citation chips.

CHALLENGE 2 — react-markdown SILENTLY DELETED EVERY CITATION.
react-markdown v9+ sanitises URLs against a safe-protocol allowlist
(`https?|ircs?|mailto|xmpp`). A custom `cite:` scheme is not on it, so every
citation href was silently blanked to an empty string and no chip would ever
render. Fixed with a `urlTransform` that passes `cite:` through untouched while
deferring everything else to `defaultUrlTransform`, so a link inside a document
still cannot smuggle in `javascript:`.

CHALLENGE 3 — FILENAMES WITH PARENTHESES BROKE CITATIONS.
`encodeURIComponent` does not escape parentheses, so a file named
`report(final).pdf` produced `](cite:report(final).pdf)` — the `)` closed the
Markdown link early and the citation degraded to plain text. Caught by a
round-trip test over spaces, unicode, ampersands, brackets and nested markup,
not by inspection. Fixed by additionally percent-encoding parentheses.

CHALLENGE 4 — RESTORED CONVERSATIONS SHOWED A BLANK ANSWER.
Reloading a conversation showed the question and the sources but an empty
answer. The typing animation decided whether a turn was mid-reveal by checking
`turn.id === latestId && typed < answer.length`. After loading history, `typed`
is 0 and no timer ever runs — so the most recent restored turn sliced its answer
to the empty string permanently. Sources still appeared because they sat outside
that check, which is what made the bug look like a data problem rather than a
rendering one. Fixed by replacing the inference with an explicit `typingTurnId`
that only the animation sets.

CHALLENGE 5 — A COLLAPSED PANEL THAT REFUSED TO COLLAPSE.
Hiding the sources list with the `hidden` attribute did nothing. Tailwind's
preflight defines `[hidden]:where(:not([hidden="until-found"]))` with
`display:none`, which has the same (0,1,0) specificity as the `.grid` utility —
so the tie is broken by source order, and utilities come after preflight.
`.grid`'s `display:grid` won. Fixed by toggling the class rather than the
attribute.

CHALLENGE 6 — THE THREE-COLUMN LAYOUT OVERLAPPED ITSELF.
Panels visibly bled into each other. Three compounding causes, all arithmetic:
  (a) The track minimums (260 + 440 + 260) plus two 28px gaps came to 1016px,
      but at the `lg` breakpoint that enabled them the content box is only
      1024 − 52 = 972px. The grid was 44px too wide at exactly the width where
      it switched on. Fixed by using `minmax(0, …)` everywhere so a track can
      always shrink, verified arithmetically at 390/768/1024/1100/1280/1440/1920.
  (b) Grid items default to `min-width: auto`, so the 36-character document
      UUID set its column's width regardless of the template — that was the
      text crossing into the neighbouring panel. Fixed with `min-w-0` on each
      column plus real truncation on the id.
  (c) `align-content` defaults to stretch, so the Ingest panel's row stretched
      to match the tallest column, producing a tall mostly-empty box. Fixed
      with `content-start`.

CHALLENGE 7 — LONG LINES AFTER GOING FULL-WIDTH.
Giving the answer the full page width introduced a typography problem: text
across ~1270px runs to roughly 200 characters per line, well past where reading
accuracy degrades. Solved by capping the prose at 76 characters and giving the
leftover width to a sources column beside it — the width is used, but for a
second column rather than longer lines.

CHALLENGE 8 — COLD START LOOKED LIKE AN OUTAGE.
The backend scales to zero, so the first visit after an idle period took ~30-60
seconds. The health probe aborted at 8 seconds and the UI said "Backend
unavailable", which reads as broken software rather than a normal wake. Fixed
with a cold-aware probe timeout, a 3-second retry while offline, a real
`/warmup` endpoint (see 6.3), and honest copy that says "Waking the backend" for
90 seconds before it will call anything unavailable — because a wake that never
finishes IS an outage, and saying otherwise would be misleading.

5. DATABASES AND STORAGE
================================================================================

This system uses four distinct storage systems, because they solve genuinely
different problems. Using one for all four would be worse at each.

5.1 QDRANT — WHAT A VECTOR DATABASE IS, AND WHY RAG NEEDS ONE
--------------------------------------------------------------------------------
WHAT IT IS. Qdrant is a vector database: a database whose primary index is over
high-dimensional vectors rather than over scalar columns. Its core operation is
"given this 1024-dimensional query vector, return the K stored vectors closest
to it", where closeness is cosine similarity.

WHY RAG CANNOT USE A NORMAL DATABASE FOR THIS. A relational index answers "where
column = value" or "where column > value". Semantic search is neither — it is
nearest-neighbour search in a continuous space. A brute-force scan comparing the
query against every stored vector is exact but O(n) per query, which stops being
viable in the thousands of chunks. Vector databases use approximate
nearest-neighbour indexes to make it sub-linear.

HNSW, THE INDEX WE RELY ON. Hierarchical Navigable Small World builds a
multi-layer proximity graph. Search starts at a sparse top layer, greedily walks
toward the query, then descends into progressively denser layers, refining. The
result is approximate — it can miss a true nearest neighbour — but it is orders
of magnitude faster, and for retrieval feeding an LLM, approximate is entirely
acceptable. We run the default m=16, ef_construct=100.

WHY QDRANT SPECIFICALLY:
  * A genuinely usable free managed tier (Qdrant Cloud), which suits a
    zero-budget deployment.
  * First-class PAYLOAD FILTERING — arbitrary JSON stored alongside each vector
    and filterable at query time. This is exactly what multi-tenancy needs: one
    shared collection, with every query filtered to `document_id` AND
    `owner_id`. That is the mechanism enforcing that one user's question can
    never retrieve another user's document.
  * Written in Rust; predictable performance and memory.

WHAT WE STORE. One shared collection per environment —
`chunks_collection_v2_staging` for dev and `chunks_collection_v2` for
production — vector size 1024, cosine distance.

A NOTE ON THE PRODUCTION COLLECTION NAME. Production originally pointed at
`chunks_collection`, which was created at vector size 1536 for
text-embedding-3-small. A Qdrant collection's vector size is FIXED at creation,
so this was not a matter of which model is used going forward: upserting
1024-dimension bge-m3 vectors into it would have been rejected outright on
dimension mismatch. Production was therefore moved to a new collection, which
the app creates on first ingest with the correct size and payload indexes. The
old collection is left in place, holding its two original points. Each point: id = uuid5(document_id,
chunk_index); vector = the bge-m3 embedding; payload = {text, metadata (source,
page, section, chunk_id), document_id, owner_id}.

THE PAYLOAD INDEX LESSON. Filtering on a payload key requires an explicit
payload index of type keyword or uuid. Without it Qdrant does not merely run
slower — it refuses the query with a 400. See challenge 7 in section 3.8.

5.2 SQLITE — THE METADATA AND HISTORY STORE
--------------------------------------------------------------------------------
Qdrant holds vectors. It is not the right place for user accounts, OTP codes, or
chat history. Those are relational, and they need transactions.

WHY SQLITE. It is in the Python standard library (no dependency, no driver, no
server), needs no separate Azure resource (so it costs nothing), and is entirely
adequate for a single-writer workload — which is guaranteed here, because
maxReplicas is 1.

SCHEMA (data/rag.db, on the mounted Azure Files volume):
  users            (id, email, email_verified, password_hash, created_at)
                   password_hash is NULL for accounts that only ever used OAuth.
  auth_identities  (id, user_id, provider, provider_user_id, created_at)
                   One row per linked provider, so the same account can sign in
                   via GitHub or Google. UNIQUE(provider, provider_user_id).
  otp_codes        (id, user_id, code_hash, purpose, expires_at, consumed_at)
                   The HASH, never the plaintext code. 10-minute expiry.
  documents        (id, owner_id, filename, ingested_at, pages, chunks,
                    indexed_chunks)
  chat_turns       (id, document_id, owner_id, question, answer, sources_json,
                    created_at)

ACCOUNT LINKING POLICY. If an OAuth login's verified email matches an existing
user, the new provider is LINKED to that account rather than creating a
duplicate. Both GitHub and Google return a verified email, which makes this
safe. Without it, signing in with Google after having signed up with GitHub
would strand your documents on an inaccessible second account.

5.3 SUPABASE — WHAT IT IS, WHY WE ARE MOVING, LIMITATIONS, MITIGATIONS
--------------------------------------------------------------------------------
STATUS: PLANNED, NOT YET IMPLEMENTED. SQLite is what runs today.

WHAT SUPABASE IS. An open-source "Firebase alternative" built around a managed
PostgreSQL database, bundling: Postgres itself, an auto-generated REST API
(PostgREST), an authentication service, file storage, edge functions, and
realtime subscriptions over Postgres logical replication.

WHAT WE WOULD ADOPT — DELIBERATELY NARROW. The DATABASE ONLY. Not Supabase Auth,
not Supabase Storage. Our authentication (JWT + OAuth + OTP) is already built,
tested, and working across three providers; replacing it would be a rewrite with
no user-visible benefit and a new external dependency in the login path — the
single worst place to add a hard dependency. Supabase would be Postgres with a
managed control plane, nothing more.

WHY MOVE AT ALL. SQLite on an SMB-mounted network share is the weakest link in
the current architecture:
  * It hard-caps horizontal scaling at maxReplicas 1 forever. Two containers
    writing to one SQLite file over SMB is data corruption, not a performance
    problem.
  * SMB does not reliably provide the byte-range locking SQLite expects, which
    already forced the `nobrl` mount option and cost a production crash-loop to
    diagnose.
  * There is no managed backup, no point-in-time recovery, and no way to query
    the data without shelling into a container.

SUPABASE FREE-TIER LIMITATIONS, AND HOW WE MITIGATE EACH:
  (a) PROJECTS PAUSE AFTER ~7 DAYS OF INACTIVITY. A paused project refuses
      connections until manually resumed. Mitigation: our backend already
      scales to zero and already has a `/warmup` path; a scheduled lightweight
      query (a cron ping) keeps the project active. This aligns well — we
      already accept and manage cold starts.
  (b) CONNECTION LIMITS. The free tier allows relatively few direct Postgres
      connections, and serverless-style workloads exhaust them by opening a new
      connection per invocation. Mitigation: connect through Supabase's built-in
      connection pooler (Supavisor/PgBouncer) in transaction mode rather than
      directly, and keep a small bounded pool in the app.
  (c) STORAGE AND EGRESS CAPS (500MB database, limited monthly egress).
      Mitigation: this is metadata only — users, documents, chat turns. The
      bulky data (vectors, BM25 indexes, original files) stays in Qdrant and
      Azure Files. Realistic metadata volume is measured in megabytes.
  (d) COLD-START LATENCY ON FIRST CONNECTION after idle. Mitigation: same
      warmup path as (a).
  (e) SHARED INFRASTRUCTURE / NOISY NEIGHBOURS on the free tier. Mitigation:
      accepted for a dev/portfolio deployment; the migration path to a paid
      instance is a connection-string change, which is precisely why adopting
      only the database matters.

WHAT WE GAIN BEYOND RELIABILITY: real concurrent writes (so maxReplicas can
exceed 1), managed backups, a SQL console, and — significantly for section 7 —
Postgres ROW-LEVEL SECURITY, which lets tenant isolation be enforced by the
database itself rather than by application code remembering to add a WHERE
clause.

MIGRATION SHAPE (when executed): schema translation (SQLite's loose typing to
real Postgres types, TEXT timestamps to timestamptz), a one-off data copy, a
repository-layer swap behind the existing db.py function boundary — which is
why db.py exposes plain functions rather than leaking sqlite3 objects to
callers — then RLS policies, then cutover.

5.4 REDIS / UPSTASH — THE CACHE TIER
--------------------------------------------------------------------------------
STATUS: LIVE ON BOTH ENVIRONMENTS. An Upstash free-tier database (256MB, 10GB
monthly bandwidth) in Mumbai (ap-south-1) — the same region as the Container
Apps backend, so the extra hop is short. The connection string is stored as a
Container App secret (`redis-url`) and referenced via secretRef on both
rag-api-staging and rag-api.

ONE DETAIL THAT MATTERS WHEN CONFIGURING IT: the scheme must be `rediss://`,
not `redis://`. redis-py negotiates TLS from the URL scheme, whereas the
`redis-cli` connection string Upstash displays uses `redis://` with a separate
`--tls` flag. Copying that string verbatim yields a client that tries to speak
plaintext to a TLS-only endpoint.

THE PROBLEM IT SOLVES. Every single query re-read that document's `bm25.pkl`
off the Azure Files SMB share before retrieval could even start. That is a
network round-trip on the hot path of every question, for a file that only
changes when the document is re-ingested.

THE DESIGN — TWO TIERS, because they fail differently:
  Tier 1: in-process LRU (bounded, default 4 entries). No serialisation, no
          network — the fastest possible. Lost on every scale-to-zero.
  Tier 2: Redis over TLS (`rediss://`). Survives scale-to-zero, which is exactly
          tier 1's weakness.
  Fallback: Azure Files, unchanged, and still the only writer.

WHY UPSTASH SPECIFICALLY. Serverless Redis with a genuine free tier and no
monthly minimum, which preserves the project's $0 running cost. Azure Cache for
Redis would be lower-latency (same region) but costs roughly $16/month billed
continuously — a standing bill for a cache the app mainly leans on after idle
periods.

CORRECTNESS PROPERTIES, ALL DELIBERATE:
  * KEYS INCLUDE owner_id (`doc:{owner_id}:{document_id}`). A key omitting the
    owner would be a way to serve one user's index to another.
  * DEGRADES SILENTLY. Unset, unreachable, or timing out — every path returns
    None and falls through to disk. A cache must never be able to fail a query.
  * INVALIDATES on delete and on re-ingest. A cache that keeps answering from
    content the document no longer contains is worse than no cache.
  * SIZE-CAPPED before writing (default 8MB), so a large document cannot blow
    the free tier's request limits; Azure Files still serves it.
  * TRUST BOUNDARY NOTED: values are pickled, so only our backend may write to
    this namespace — TLS plus token auth, and no user-supplied key ever reaches
    it.

5.5 AZURE FILES — THE SHARED VOLUME
--------------------------------------------------------------------------------
An SMB file share mounted at /home/appuser/app/data, holding data/rag.db and
data/documents/{owner_id}/{document_id}/bm25.pkl. It exists because container
filesystems are ephemeral and scale-to-zero would otherwise destroy every
account and every index on each wake. Its limitations (SMB locking, latency) are
covered in 3.8 and 5.4.

NOTE: the baked model weights deliberately do NOT live here. They are in the
image at /opt/models, because reading 2.3GB over SMB on every cold start would
reintroduce the exact latency the baking was meant to remove.

6. CLOUD INFRASTRUCTURE — MICROSOFT AZURE
================================================================================

6.1 THE STUDENT CREDIT CONSTRAINT
--------------------------------------------------------------------------------
This entire platform is built and operated on an Azure for Students
subscription: $100 of credit, no credit card required, and — critically — the
subscription carries policy restrictions that a normal pay-as-you-go account
does not. That constraint is not a footnote; it drove several of the biggest
architectural decisions in the project.

Consequences that shaped the design:
  * The `sys.regionrestriction` policy capping deployable regions to five is
    what forced the four-attempt model search in section 3.5.
  * "Scale to zero or do not deploy it" became a hard rule. Any always-on GPU
    or always-warm instance would consume the entire credit in weeks.
  * Self-hosting embeddings instead of using a metered API is a direct
    consequence of wanting embedding cost to be structurally $0 rather than
    proportional to usage.

RUNNING COST TODAY: approximately $0/month. Container Apps' free monthly grant
covers the compute at this usage level, Qdrant Cloud and Upstash have free
tiers, GitHub Pages and Actions are free for public repositories, and Azure
OpenAI is billed per token at fractions of a cent.

THE COST DECISION WE EXPLICITLY REJECTED: setting minReplicas to 1 to eliminate
cold starts entirely. Confirmed cost approximately $50-51/month, billed 24/7
regardless of traffic — roughly half the total credit every month, on days with
zero users, purely to avoid a ~30 second wait. Rejected. The engineering effort
went into making the wake fast and honest instead (6.3).

6.2 AZURE SERVICES IN USE
--------------------------------------------------------------------------------
(1) AZURE CONTAINER APPS — the application host.
    Two apps: `rag-api-staging` (dev) and `rag-api` (production), in Central
    India, in the `rag-api-env` managed environment. Serverless containers with
    KEDA-based autoscaling, minReplicas 0 and maxReplicas 1. Resources: 2 vCPU,
    4GB RAM, 8GB ephemeral storage.
    Operationally important properties learned the hard way:
      * Revisions are immutable; `activeRevisionsMode: Single`.
      * Traffic weight and health state are INDEPENDENT (see challenge 11).
      * Ingress severs requests at roughly 240 seconds — the reason async
        ingest exists.
      * Images are cached per node, so repeat activations pull in ~20ms even
        for a large image.

(2) AZURE OPENAI SERVICE — generation.
    gpt-5-mini, Global Standard deployment, in UAE North (the only one of the
    five permitted regions with a current model catalog).

(3) AZURE FILES (Storage Account) — the persistent volume. See 5.5.

(4) AZURE COMMUNICATION SERVICES (Email) — OTP delivery. See 6.4.

(5) AZURE AI DOCUMENT INTELLIGENCE — the paid OCR tier of the parser router,
    using prebuilt-read and prebuilt-layout only. See 3.6.

(6) LOG ANALYTICS WORKSPACE — centralised logs. ContainerAppConsoleLogs_CL for
    application output and ContainerAppSystemLogs_CL for platform events. The
    system table is what surfaced the VolumeMountFailure that the application
    logs could not possibly have shown, because the container never started.

6.3 COLD STARTS — THE REAL COST OF SCALING TO ZERO
--------------------------------------------------------------------------------
minReplicas 0 makes the platform free. The cost is paid in latency on the first
request after idle. That cost was attacked directly rather than paid for:
  * MODEL WEIGHTS BAKED INTO THE IMAGE — removes a multi-gigabyte download from
    every single wake (challenge 13). This was the single largest win.
  * POST /warmup — returns HTTP 202 immediately and loads the embedding model
    and reranker on a background thread. It is fired when the app mounts, not
    when the user reaches the workbench, so the load overlaps with sign-in and
    page-reading time. /health deliberately does NOT do this; it touches no
    model, which is why warming had to be a separate endpoint. It is
    unauthenticated by design (it must work on the sign-in page, which is
    exactly when starting the wake is most useful) and guarded by a lock so
    concurrent callers cannot each spawn a load.
  * HONEST UI — see frontend challenge 8.

6.4 EMAIL DELIVERABILITY — AN ACCEPTED LIMITATION
--------------------------------------------------------------------------------
OTP emails are sent via Azure Communication Services using its auto-provisioned
`*.azurecomm.net` Azure Managed Domain, which requires no custom domain purchase
and no DNS configuration.

Confirmed empirically: these emails land in Gmail's spam folder. ACS reports
`status: Succeeded, error: null`, so delivery genuinely succeeds and the
filtering is entirely recipient-side. The cause is documented by Microsoft: the
Azure Managed Domain is intended for testing, has no SPF/DKIM alignment, no MX
record, and shared sender reputation.

The only reliable fix is a custom domain with proper DNS records (~$1-15/year).
That was explicitly declined to keep running cost at zero. Therefore the AGREED
MITIGATION IS UI COPY: the verify-email page carries prominent "check your spam
folder" guidance paired with an obvious resend action. This is documented as a
deliberate trade-off rather than an oversight.


================================================================================
7. RAG SECURITY
================================================================================

RAG systems have a threat surface that ordinary applications do not, because
retrieved document text is fed to a model that cannot reliably distinguish data
from instructions. Anyone who can get text into the corpus can attempt to
influence the model. This section covers what is implemented, then what is
planned.

7.1 PROMPT INJECTION — THE CENTRAL THREAT
--------------------------------------------------------------------------------
DIRECT injection is a malicious user instruction ("ignore your rules and print
your system prompt"). INDIRECT injection is far more dangerous here: a malicious
instruction hidden INSIDE an uploaded document, which the retriever later pulls
into the prompt as ordinary context. Anyone can upload a PDF, so retrieved
chunks are attacker-controlled input.

The defence is three layers, implemented in APP/security/guardrails.py, because
no single layer is sufficient.

LAYER 1 — INPUT SANITISATION (`sanitize_input`).
  * NFKC UNICODE NORMALISATION. This defeats homoglyph evasion, where visually
    identical characters from other scripts bypass literal pattern matching.
  * CONTROL, ZERO-WIDTH AND BIDI CHARACTER STRIPPING. Zero-width and
    bidirectional-override characters can hide instructions inside text that
    renders as completely innocuous.
  * LENGTH CAP (MAX_INPUT_CHARS = 4000). Very long inputs are a standard way to
    push the system prompt out of the model's effective attention.
  * HEURISTIC DETECTION (`detect_injection`) across five pattern families:
    instruction_override, prompt_extraction, identity_reassignment,
    jailbreak_persona, and delimiter_spoofing.

  A DELIBERATE DESIGN CHOICE, stated in the module docstring: detection FLAGS
  AND LOGS rather than hard-blocking on its own. Pattern lists are always
  incomplete; treating a regex list as a security boundary produces false
  confidence and false positives in equal measure. The structural boundary in
  layer 2 is the actual control.

LAYER 2 — THE UNTRUSTED-DATA BOUNDARY (`build_rag_payload`). THE MOST IMPORTANT
LAYER, and the one that was missing originally.
  Retrieved chunks are enclosed in explicit markers:
      <<<UNTRUSTED_DATA_CONTEXT_START>>>
      ... retrieved document text ...
      <<<UNTRUSTED_DATA_CONTEXT_END>>>
  The system prompt states that everything between those markers is DATA to be
  read, never instructions to be followed. Before this existed, chunks were
  interpolated straight into the prompt as `CONTEXT:\n{...}`, where a line
  reading "ignore previous instructions" is structurally indistinguishable from
  a genuine one.
  MARKER SPOOFING IS NEUTRALISED (`neutralize_context`): a document containing
  the marker text itself cannot close the boundary early and escape into the
  instruction region.

LAYER 3 — OUTPUT VALIDATION (`validate_output`). Checks what the model actually
produced before it reaches the user, in case layers 1 and 2 were bypassed. Three
leak categories are matched: verbatim system-prompt phrases, boundary markers,
and infrastructure identifiers (collection names, `bge-m3`, `gpt-5-mini`,
`qdrant`, the Container Apps hostname, `secretref:`, `hnsw_ef`). A response that
matches is replaced rather than returned.

A FOURTH, SUBTLE PROTECTION: the query-rewrite step is SKIPPED when the question
matches injection patterns. A rewriter that helpfully "tidies up" an attack
would launder it past the very filters designed to catch it — the raw text has
to survive to stay detectable.

DEFENCE IN DEPTH IN THE PROMPT ITSELF: the system prompt lives in prompts/,
deliberately outside APP/, so the security rules are reviewable on their own.
Its absence from the Docker image was a real bug — `build_rag_payload` would
have raised FileNotFoundError in production — fixed by explicitly copying
prompts/ into the image.

7.2 AUTHENTICATION AND AUTHORISATION
--------------------------------------------------------------------------------
LOGIN IS MANDATORY. Every route except /health, /warmup and the /auth/* routes
themselves requires a valid token. There is no anonymous ingest or query path.
The previous `SHARED_API_KEY` — a single static string compared against a header,
which is a deterrent rather than authentication — was RETIRED entirely rather
than kept alongside.

JWT (JSON Web Tokens). On successful sign-in the backend issues a signed token
whose `sub` claim is the internal user id, with a short expiry. Every subsequent
request carries `Authorization: Bearer <token>`. The signature is verified with
a server-side secret (`JWT_SECRET_KEY`, a Container App secret) on every
request, so a tampered token is rejected. The token is a bearer credential, not
an identity claim to be trusted at face value: `get_current_user` decodes and
verifies it, and returns 401 on any failure.

OAUTH 2.0 — AUTHORIZATION CODE FLOW, for GitHub and Google. Worth stating
precisely what this buys: the user authenticates with the PROVIDER, and this
application never sees their password. The browser receives a short-lived
authorization CODE, which is exchanged SERVER-SIDE for an access token, so the
client secret never reaches the browser. We then read the provider's verified
email and profile, apply the account-linking policy from 5.2, and issue our own
JWT. Provider tokens are not stored.
  CSRF PROTECTION: the `state` parameter is generated per attempt, stored in
  sessionStorage, and compared on return — a code delivered with a state this
  browser never issued did not come from a sign-in this browser started. It
  simultaneously carries which provider initiated the flow, which is what allows
  one shared callback page for both.
  OPERATIONAL NOTE: GitHub OAuth Apps allow exactly ONE callback URL, which is
  why production and dev require separate apps. Google allows multiple redirect
  URIs on a single client. Client IDs are public and safe to bake into a static
  bundle; client SECRETS are backend-only Container App secrets.

EMAIL + PASSWORD WITH OTP ACTIVATION.
  * Passwords hashed with BCRYPT — a deliberately slow, salted, adaptive hash.
    The plaintext is never stored, never logged.
  * Accounts are created with `email_verified = false` and CANNOT log in until
    verified, which prevents signup with an address the user does not control.
  * A 6-digit OTP is generated; only its HASH is stored, with a 10-minute
    expiry and a `consumed_at` marker so a code is single-use.
  * Resend is cooldown-limited (1/minute) INDEPENDENTLY of the general rate
    limiter, because OTP endpoints are a standing abuse target — an email-send
    endpoint without a cooldown is both a spam vector and a cost vector.

7.3 RATE LIMITING AND ABUSE CONTROL
--------------------------------------------------------------------------------
Implemented with `slowapi`, keyed by the AUTHENTICATED USER ID rather than by IP
address. Since login is mandatory, every request has a real identity, which
makes per-user limits both possible and fairer than IP limits (IP limits punish
shared networks and are trivially evaded).

  POST /ingest : 10/hour/user   (INGEST_RATE_LIMIT)
  POST /query  : 60/hour/user   (QUERY_RATE_LIMIT)

Both are environment-overridable without a code change. Exceeding a limit
returns HTTP 429.

WHY THESE ENDPOINTS SPECIFICALLY: they are the ones that cost real money and
real CPU. /ingest runs OCR (metered per page) and a full embedding pass; /query
runs up to two LLM calls. An unlimited endpoint that calls a paid API is a
financial denial-of-service waiting to happen.

ADDITIONAL BOUNDED-RESOURCE CONTROLS:
  * MAX_CONTEXT_TOKENS caps the prompt so a dense document cannot silently
    produce an oversized (and expensive) request.
  * The cache size cap (8MB) bounds what can be pushed into Redis.
  * The in-process LRU is bounded (4 entries) so cache growth cannot exhaust
    container memory.
  * Ingest request size and accepted extensions are constrained at the API.

7.4 TENANT ISOLATION — THE MOST IMPORTANT PROPERTY
--------------------------------------------------------------------------------
For a multi-user document system, the single worst possible bug is one user
seeing another user's document. Isolation is enforced at every layer
independently, so that no single mistake is sufficient to break it:

  * VECTOR SEARCH: every Qdrant query filters on BOTH document_id AND owner_id.
  * FILESYSTEM: BM25 indexes live under data/documents/{owner_id}/{document_id}/,
    so the owner is part of the path.
  * DATABASE: every documents and chat_turns query is scoped by owner_id, and
    /documents/{id} returns 404 (not 403) for another user's id — not leaking
    whether the id exists.
  * CACHE: keys are namespaced `doc:{owner_id}:{document_id}`. This was called
    out explicitly in the cache module because a key omitting the owner would be
    a silent cross-tenant leak, and it was verified with a test asserting that a
    second owner cannot read the first's cached entry.

7.5 TRANSPORT, HEADERS AND SECRETS
--------------------------------------------------------------------------------
  * HTTPS EVERYWHERE. GitHub Pages and Container Apps both terminate TLS;
    Container Apps issues and renews managed certificates.
  * CORS IS AN ALLOWLIST, not a wildcard: only the known frontend origins are
    permitted, with an explicit method and header list, and
    `allow_credentials=False` (no cookies are used — wildcard plus credentials
    is invalid anyway).
  * SECRETS ARE NEVER IN THE REPOSITORY. All secrets are Container App secrets
    referenced via `secretRef`, or GitHub Actions secrets. `.env` is
    gitignored. The frontend receives only public values (OAuth client IDs,
    API base URL).
  * BYO OPENAI KEYS ARE NEVER PERSISTED — browser-local, sent per request,
    used for that request, discarded.
  * NON-ROOT CONTAINER. The image runs as `appuser`, not root.
  * REQUEST IDs. Every request carries an `X-Request-ID` through structured
    logs, so an incident can be traced without logging request bodies.

7.6 PLANNED — PII DETECTION AND REDACTION
--------------------------------------------------------------------------------
STATUS: PLANNED, NOT YET IMPLEMENTED.

WHAT PII DETECTION IS. Personally Identifiable Information is any data that
identifies a specific person: names, email addresses, phone numbers, physical
addresses, national identifiers (Aadhaar, SSN, PAN), passport and licence
numbers, payment card numbers, dates of birth, IP addresses, and medical or
biometric identifiers. PII detection is the automated process of finding these
in unstructured text; redaction is replacing them with placeholders such as
`<PERSON_1>` or `<EMAIL_1>`.

WHY IT MATTERS SPECIFICALLY FOR RAG. A RAG system is unusually exposed, for
three distinct reasons:
  (a) Users upload documents that plausibly contain third-party personal data
      — resumes, contracts, medical records, HR files — often without having
      considered that it will be sent to a model provider.
  (b) Retrieved chunks are sent to an external LLM API on every question, so
      PII in a document crosses a trust boundary repeatedly, not once.
  (c) Answers and their source excerpts are PERSISTED in chat_turns, so PII
      accumulates in our own database as a durable secondary copy.
  Under regulations such as GDPR and India's DPDP Act, that combination creates
  concrete obligations around consent, minimisation, and erasure.

HOW WE PLAN TO IMPLEMENT IT. A hybrid approach, because neither technique alone
is adequate:
  1. DETERMINISTIC PATTERN MATCHING for structured identifiers with verifiable
     formats — email addresses, phone numbers, credit cards (validated with the
     Luhn checksum to cut false positives), Aadhaar, PAN, IP addresses. High
     precision, near-zero cost, catches the majority of real cases.
  2. NAMED ENTITY RECOGNITION for unstructured identifiers that have no fixed
     format — person names, organisations, locations. The intended tool is
     MICROSOFT PRESIDIO, which is purpose-built for exactly this, is open
     source, runs locally (so detection itself does not leak the data it is
     detecting), wraps spaCy NER, and ships with recognisers for many national
     identifier formats plus a pluggable anonymisation engine.
  3. INTEGRATION AT THREE POINTS:
     - AT INGEST: scan extracted text, record what categories were found, and
       surface a clear warning to the uploader before indexing proceeds.
     - BEFORE THE LLM CALL: redact detected PII from the assembled context, so
       placeholders rather than real identifiers cross the network to the model
       provider.
     - BEFORE PERSISTENCE: store redacted source excerpts in chat_turns.
  4. REVERSIBLE MAPPING held only in memory for the lifetime of a request, so
     the answer returned to the legitimate document owner can be re-populated
     with the real values while the external API only ever saw placeholders.
  5. USER CONTROL: a per-document toggle, because for some legitimate use cases
     (querying your own resume, which is precisely the test document used
     throughout this project) redaction would destroy the utility of the answer.

KNOWN TRADE-OFFS TO MANAGE: NER adds CPU cost to ingest on a container that is
already CPU-bound; false positives can redact meaningful content and damage
answer quality; and no detector is exhaustive, so this must be presented as risk
reduction rather than a guarantee.

7.7 PLANNED — POSTGRES ROW-LEVEL SECURITY (RLS)
--------------------------------------------------------------------------------
STATUS: PLANNED, arriving with the Supabase migration (5.3).

WHAT RLS IS. A PostgreSQL feature that attaches security POLICIES directly to
tables. Once enabled, every query — regardless of which application, ORM, or
console issued it — is silently and unavoidably filtered by the policy
predicate. A policy such as `USING (owner_id = current_setting('app.user_id'))`
means a plain `SELECT * FROM documents` physically cannot return another
tenant's rows.

WHY IT IS A MEANINGFUL UPGRADE. Today, tenant isolation depends on application
code remembering to include `WHERE owner_id = ?` in every query. That discipline
is currently correct and tested — but it is discipline, and one forgotten clause
in one future endpoint is a cross-tenant data leak. RLS moves the guarantee from
convention into the database engine, which is the difference between "we are
careful" and "it is not possible". It is defence in depth: the application would
keep its explicit filters, and RLS would independently enforce the same rule.

HOW WE WOULD IMPLEMENT IT: enable RLS on documents, chat_turns and
auth_identities; set `app.user_id` from the verified JWT at the start of each
transaction; write per-table SELECT/INSERT/UPDATE/DELETE policies; and connect
as a role that is NOT the table owner, since table owners bypass RLS by default
— a detail that silently defeats the whole mechanism if missed.

7.8 PLANNED — LLM FIREWALL / GATEWAY
--------------------------------------------------------------------------------
STATUS: CONCEPTUAL.

An "LLM firewall" is a dedicated inspection layer sitting between the
application and the model provider, screening both directions: inbound prompts
for injection, jailbreaks and policy violations; outbound completions for PII
leakage, toxicity, and system-prompt disclosure. Options include Azure AI
Content Safety's Prompt Shields, Llama Guard, and NVIDIA NeMo Guardrails.

Our current guardrails already implement the same three-stage shape in-process
(input inspection, structural boundary, output validation). A dedicated firewall
would add centralised policy management, maintained and continuously updated
detection rules, and per-request audit logging suitable for compliance. The
honest assessment is that the STRUCTURAL boundary in layer 2 is doing most of
the real work today, and a firewall's classifier-based detection would be an
additional probabilistic layer on top rather than a replacement for it.


================================================================================
8. RAG EVALUATION AND METRICS (RAGAS)
================================================================================

8.1 WHY RAG NEEDS ITS OWN EVALUATION DISCIPLINE
--------------------------------------------------------------------------------
"The answers look good" is not evaluation. A RAG system can fail in several
distinct ways that a single quality impression cannot separate:
  * Retrieval fetched the wrong chunks, and the model answered well from bad
    context.
  * Retrieval fetched the right chunks, and the model ignored them.
  * Retrieval fetched the right chunks, and the model added a plausible detail
    that is not in them.
Each has a different fix — chunking, prompting, model choice — so the metrics
must separate RETRIEVAL quality from GENERATION quality.

8.2 RAGAS — WHAT IT IS
--------------------------------------------------------------------------------
RAGAS (Retrieval-Augmented Generation Assessment) is an open-source framework
for evaluating RAG pipelines. Its central idea is LLM-as-judge: rather than
requiring a large hand-labelled test set, it uses a strong model to decompose
answers into individual claims and verify each against the retrieved context.
This makes reference-free evaluation practical — several of its metrics need no
ground-truth answer at all.

IMPLEMENTED: eval/ragas_evaluation.py, an offline harness that runs the real
retrieval pipeline over a question set and scores it. It uses OpenAI models for
generation and judging (gpt-4o-mini by default, configurable), with concurrency
controls (EVAL_CONCURRENCY, GEN_CONCURRENCY) because LLM-as-judge is
rate-limit-bound. Results and generation caches are written under evals/.

8.3 THE FOUR METRICS WE MEASURE
--------------------------------------------------------------------------------
(1) FAITHFULNESS — generation quality. Of the claims made in the answer, what
    fraction are supported by the retrieved context? This is the direct
    hallucination measure and the single most important number for this
    project, because the entire value proposition is groundedness. A low score
    means the model is inventing, and points at prompting or model choice.

(2) ANSWER RELEVANCY — generation quality. Does the answer actually address the
    question asked? Computed by generating questions from the answer and
    measuring their similarity to the original. Catches answers that are
    faithful to the context but evasive or off-target.

(3) CONTEXT PRECISION — retrieval quality. Of the chunks retrieved, what
    fraction are actually relevant, and are the relevant ones ranked highly?
    Low precision means noise is being fed to the model, which wastes context
    budget and increases the chance of the model latching onto something
    irrelevant. This is the metric that most directly grades the reranker.

(4) CONTEXT RECALL — retrieval quality. Of the information needed to answer,
    what fraction was actually retrieved? This is the metric that grades
    CHUNKING and the retriever together. Low recall means the answer was never
    retrievable in the first place, and no amount of prompt engineering will
    fix it.

READING THEM TOGETHER IS THE POINT: high faithfulness with low context recall
means the system is honestly saying "I don't know" to answerable questions —
which is a retrieval bug wearing the costume of good behaviour, and it is
exactly the failure mode a single "does it look right" check would miss.

8.4 EVALUATION BEYOND RAGAS, ALREADY PERFORMED
--------------------------------------------------------------------------------
  * A/B RETRIEVAL COMPARISON (scripts/compare_chunking_retrieval.py) — used to
    settle structure-aware versus recursive chunking on actual retrieval
    quality rather than on chunk-count statistics, after it was pointed out
    that faster is not the same as better.
  * OUT-OF-DOMAIN JUDGING — the eval harness includes an OOD judge, checking
    that questions the document cannot answer are correctly refused. A system
    that never refuses is not grounded, it is merely confident.
  * INGEST PERFORMANCE BENCHMARKS — wall-clock timings on a fixed 44-page PDF
    used as the like-for-like baseline throughout (section 3.2).
  * UNIT AND INTEGRATION TESTS — tests/ covers guardrails, the Phase 1 data
    model, provider abstraction, async jobs, structure chunking, and the parser
    router. One genuine bug was caught here that inspection had missed: the
    parser router counted a SKIPPED (unconfigured) tier as a fallback, because
    it tested `index > 0` instead of `len(attempted) > 1`.

8.5 FUTURE SCOPE — LANGSMITH AND CONTINUOUS EVALUATION
--------------------------------------------------------------------------------
STATUS: EXPLORATORY, NOT IMPLEMENTED.

WHAT LANGSMITH IS. An observability and evaluation platform from the LangChain
team, built specifically for LLM applications. It provides distributed TRACING
of every step in a chain (retrieval, reranking, prompt assembly, generation)
with inputs, outputs, latency and token cost at each step; DATASET management
for curated test cases; automated evaluators that can run on those datasets; and
production monitoring with human feedback collection.

WHY IT WOULD HELP THIS PROJECT SPECIFICALLY:
  * Our per-stage millisecond logging (section 3.1, step 15) is a hand-rolled
    version of what tracing gives properly — LangSmith would show WHICH chunks
    were retrieved for a slow query, not merely that retrieval took 400ms.
  * REGRESSION DETECTION. Today, changing the chunker means manually re-running
    an evaluation. A curated dataset with automated evaluators in CI would fail
    a pull request that degraded faithfulness, turning RAG quality into
    something the build enforces rather than something someone remembers to
    check.
  * PRODUCTION FEEDBACK. Thumbs up/down on real answers, correlated back to the
    exact retrieved context, is the highest-quality evaluation data obtainable —
    it comes from real questions rather than synthetic ones.
  * COST ATTRIBUTION per query, including the rewrite call, which currently has
    to be inferred from logs.

ALTERNATIVES WORTH WEIGHING: Langfuse (open source, self-hostable — which suits
this project's privacy stance and $0 budget better), Phoenix/Arize, and
OpenTelemetry-based tracing with a generic backend. Langfuse is the more likely
choice precisely because self-hosting keeps document text out of a third-party
observability platform, which would otherwise reintroduce the exact data-egress
concern that self-hosted embeddings were chosen to avoid.

9. DEPLOYMENT, DOCKER, AND CI/CD
================================================================================

9.1 DEPLOYMENT RESEARCH — EVERY OPTION EVALUATED, AND THE VERDICTS
--------------------------------------------------------------------------------
Deployment was not a default. Each layer of the stack was researched against a
specific set of constraints, and the constraints are what make the verdicts
make sense:

  CONSTRAINT A — A HARD $0/MONTH TARGET. The budget is $100 of Azure student
    credit with no card attached. Anything billed continuously consumes the
    entire budget regardless of whether a single person uses the app.
  CONSTRAINT B — THE WORKLOAD IS SPIKY AND MOSTLY IDLE. A portfolio/dev
    deployment sits unused for hours, then does something CPU-heavy for a
    minute. Paying for idle is paying for nothing.
  CONSTRAINT C — LARGE MEMORY FOOTPRINT. The container holds a 2.3GB embedding
    model in RAM. This immediately eliminates most "free tier" PaaS options,
    which cap at 512MB.
  CONSTRAINT D — LONG-RUNNING REQUESTS. Ingest can take minutes.
  CONSTRAINT E — PERSISTENT STORAGE for SQLite and BM25 indexes across
    restarts.

BACKEND HOSTING — OPTIONS EVALUATED:

  * AZURE CONTAINER APPS — ✅ CHOSEN. See 9.2.

  * AZURE APP SERVICE — REJECTED. The Linux free tier (F1) caps at 1GB RAM,
    which cannot hold bge-m3, and does not support custom containers on the
    free plan. The paid tier (B1) that would work is billed continuously,
    violating constraint A.

  * AZURE KUBERNETES SERVICE (AKS) — REJECTED. The control plane is free but
    the node pool is not, and nodes are billed 24/7. Enormous operational
    complexity — ingress controllers, cert-manager, HPA tuning — for a
    single-container application. Correct answer at a scale this project is
    nowhere near.

  * AZURE FUNCTIONS (serverless) — REJECTED, and instructively so. It scales to
    zero, which fits perfectly. But the Consumption plan enforces a hard
    execution timeout (default 5 minutes, max 10) which conflicts with
    constraint D, memory caps below what the embedding model needs
    (constraint C), and — decisively — a per-invocation execution model means
    the 2.3GB model would be loaded on a cold start with no guarantee the next
    invocation reuses the same warm instance. Loading a 2.3GB model per
    invocation is architecturally wrong for this workload.

  * AZURE CONTAINER INSTANCES (ACI) — REJECTED. Genuinely simple, but it has no
    scale-to-zero: a container group runs until you stop it and is billed per
    second the whole time. It is a good fit for batch jobs, not a web API that
    must be reachable but is usually idle.

  * RENDER / RAILWAY / FLY.IO — REJECTED, though these were serious candidates.
    Render's free web services sleep after inactivity (which we want) but cap
    at 512MB RAM (constraint C, fatal). Railway moved to a usage-based model
    with a small monthly credit that a 4GB-RAM service exhausts quickly. Fly.io
    genuinely supports scale-to-zero with `auto_stop_machines` and would have
    worked technically — the deciding factor was that the project already had
    $100 of Azure credit that could not be spent anywhere else, and using it
    was strictly better than spending real money elsewhere.

  * SELF-HOSTING ON A VPS — REJECTED. A $5/month VPS is real money billed
    continuously, and it moves TLS certificates, OS patching, process
    supervision, and log rotation into scope for no benefit at this scale.

  * HUGGING FACE SPACES — REJECTED for the primary API. The free CPU tier is
    attractive and would hold the model, but Spaces is optimised around
    Gradio/Streamlit demo apps, sleeps aggressively, and offers no persistent
    writable volume suitable for SQLite. Worth revisiting purely as a public
    demo mirror.

9.2 WHY AZURE CONTAINER APPS WON, AND WHAT IT COST US
--------------------------------------------------------------------------------
WHAT IT IS. A serverless container platform built on Kubernetes and KEDA, with
the Kubernetes hidden. You supply an image and a scale rule; it runs the
container, terminates TLS, issues certificates, and load-balances.

WHY IT WON, mapped directly to the constraints:
  * SCALES TO ZERO (minReplicas 0) — the single decisive feature. At idle the
    replica count is 0 and compute cost is 0 (constraints A and B).
  * A GENEROUS FREE MONTHLY GRANT covering the vCPU-seconds and GiB-seconds
    this workload consumes, which is why the real bill is ~$0.
  * ARBITRARY MEMORY within limits — 2 vCPU and 4GB RAM is configurable and
    holds the model comfortably (constraint C).
  * AZURE FILES VOLUME MOUNTS for persistence (constraint E).
  * REVISIONS — immutable deployments with traffic splitting, so a rollback is
    re-pointing traffic rather than rebuilding.
  * MANAGED TLS CERTIFICATES, issued and renewed without intervention.

WHAT IT COST US — the honest side of the ledger, all learned the hard way:
  * COLD STARTS. Scaling to zero means the first request after idle waits for a
    container to start AND for the model to load. Section 6.3 covers the
    mitigations; the cost is real and cannot be fully removed without paying
    for an always-warm replica.
  * A ~240 SECOND INGRESS TIMEOUT, which is precisely why async ingest exists
    (3.7). This is not configurable upward to an arbitrary value.
  * TRAFFIC WEIGHT AND HEALTH ARE INDEPENDENT. A revision can hold 100% of
    traffic while Unhealthy with zero replicas — the platform will not
    automatically move traffic to a healthy older revision. This cost a
    production outage to discover (9.9).
  * VOLUME MOUNT FAILURES ARE INVISIBLE TO APPLICATION LOGS, because the
    container never starts. They only appear in ContainerAppSystemLogs_CL.
  * SMB SEMANTICS. Azure Files is SMB, and SQLite's locking expectations do not
    survive that intact — hence the `nobrl` mount option.

9.3 FRONTEND HOSTING — INCLUDING THE DETOUR WE TOOK AND REVERTED
--------------------------------------------------------------------------------
The frontend is a Next.js app exported to fully STATIC files. That decision came
first and constrains the rest: with no server-side rendering there is no Node
server to host, so hosting is a static file problem.

  * GITHUB PAGES — ✅ CHOSEN. Free for public repositories with no quota
    anxiety, integrated with the CI already running there, custom domains and
    TLS supported, and a global CDN. Its one real constraint shaped the whole
    workflow: PAGES PUBLISHES EXACTLY ONE ARTIFACT PER REPOSITORY, so two
    environments cannot be deployed independently. See 9.7.

  * VERCEL — REJECTED, despite being the most natural home for Next.js. The
    Hobby tier is free but licensed for non-commercial use, and the whole point
    of choosing static export was to not need Vercel's server-side features.
    Adding a third vendor for something GitHub already does was not worth it.

  * NETLIFY — REJECTED for effectively the same reasons.

  * AZURE STATIC WEB APPS — REJECTED AFTER ACTUALLY IMPLEMENTING IT. This is
    worth recording honestly because it was a genuine wrong turn: the whole
    workflow was rewritten to deploy to Azure SWA on the reasoning that
    consolidating on one cloud was tidier. It was then reverted to GitHub Pages
    at the user's direction. The lesson retained: "everything in one vendor" is
    an aesthetic preference, not a technical argument, and it does not
    outweigh a working, free, already-integrated deployment.

9.4 VECTOR DATABASE HOSTING RESEARCH
--------------------------------------------------------------------------------
  * QDRANT CLOUD — ✅ CHOSEN. A genuinely usable free tier (1GB cluster, no
    time limit), first-class payload filtering — which is the mechanism
    enforcing tenant isolation (5.1) — written in Rust with predictable memory
    behaviour, and a clean migration path to self-hosting since it is open
    source. Note the deployment reality: the free cluster is hosted on AWS
    us-east, so vector search is a cross-cloud, cross-continent call from the
    Central India backend. Accepted, because retrieval latency is dominated by
    generation anyway.

  * SELF-HOSTED QDRANT IN THE SAME CONTAINER — REJECTED. It would eliminate the
    cross-cloud hop, but Qdrant needs persistent storage and memory of its own,
    and co-locating it with the API in a scale-to-zero container means the
    index is cold-started along with everything else.

  * PINECONE — REJECTED. The managed experience is excellent, but the free tier
    has historically been restrictive on index count and has moved terms
    repeatedly; being fully proprietary means no self-hosting escape hatch.

  * WEAVIATE — REJECTED. Very capable and open source, but heavier to operate,
    and its free managed sandbox expires (14 days), which is disqualifying for
    anything meant to stay up.

  * pgvector (Postgres extension) — REJECTED FOR NOW, BUT THE MOST INTERESTING
    ALTERNATIVE. With the planned Supabase migration (5.3) the project will
    already have a Postgres instance, and pgvector would collapse two databases
    into one, giving transactional consistency between metadata and vectors. It
    was rejected today for two reasons: at the time of the decision there was
    no Postgres in the stack at all, and pgvector's index types (IVFFlat/HNSW)
    are less mature under heavy payload filtering than Qdrant's. Worth
    re-evaluating after the Supabase migration lands.

  * CHROMA / FAISS — REJECTED. FAISS is a library, not a server — no
    persistence, filtering, or concurrent access story. Chroma is excellent for
    local prototyping but its managed hosting was immature when this was
    decided.

9.5 DOCKER — IMAGE DESIGN DECISIONS
--------------------------------------------------------------------------------
The API image is a multi-stage build (docker/Dockerfile.api). Each decision in
it exists for a measured reason.

(1) MULTI-STAGE BUILD. A builder stage creates a virtualenv and installs
    dependencies; the runtime stage copies only /opt/venv. Build tools and pip
    caches never reach the final image.

(2) CPU-ONLY TORCH, INSTALLED FIRST — THE SINGLE BIGGEST SIZE WIN.
        RUN pip install torch --index-url https://download.pytorch.org/whl/cpu
    PyPI's default Linux torch wheel bundles the full CUDA stack
    (nvidia-cublas, cudnn, triton and friends — multiple gigabytes) even though
    bge-m3 only ever runs on CPU here. Installing the CPU wheel BEFORE the main
    requirements satisfies sentence-transformers' `torch` dependency so pip
    never reaches for the CUDA build. This is the same GPU-cost trap that ruled
    out Phi-4, arriving through a transitive dependency instead of a model
    choice.

(3) A DEDICATED MODEL STAGE. Weights are downloaded in their own stage keyed
    only to docker/fetch_models.py, then copied in. See 9.8 for why the obvious
    alternative placement is wrong.

(4) NON-ROOT USER. The container runs as `appuser`, created in the image, never
    as root.

(5) `COPY --chown` RATHER THAN A FOLLOWING `chown -R`. A separate ownership
    pass rewrites every file into a new layer, which would put 2.3GB of weights
    into the image twice.

(6) EXPLICIT `COPY prompts/`. The prompts directory sits outside APP/ so the
    security rules are reviewable on their own — which means it needs copying
    explicitly. Its absence was a real bug: build_rag_payload would have raised
    FileNotFoundError in production, silently disabling the prompt-injection
    boundary.

(7) A HEALTHCHECK instruction, so the platform can tell running from healthy.

(8) A BUILD-TIME OFFLINE VERIFICATION STEP that loads the model with the
    network forced off. A wrong cache path fails silently at runtime — the app
    just downloads again, which is exactly the behaviour the baking removes —
    so it is caught in the build instead. It has already caught one real bug
    (challenge 14).

(9) `.dockerignore` excludes .git, .venv, data/, tests/, docs and the whole
    docker/ directory — with an explicit exception for fetch_models.py, which
    must reach the build context or the COPY fails outright.

RESULTING IMAGE: roughly 480MB before the model layer, roughly 2.9GB with it.
That size is deliberate and is paid on image pull, which Container Apps caches
per node — observed repeat pulls complete in about 20ms — versus a multi-gigabyte
HuggingFace download on every single cold start.

9.6 LOCAL DEVELOPMENT WITH DOCKER COMPOSE
--------------------------------------------------------------------------------
docker-compose.yml runs the full stack locally: the API, a local Qdrant with a
named volume, and the frontend. It exists so that "works on my machine" and
"works in production" are the same container image rather than two different
environments.

Two details worth recording:
  * A `./data` bind mount reproduces the Azure Files volume, so per-document
    BM25 paths and the SQLite database behave locally the way they do deployed.
  * There is deliberately NO model-cache mount any more. It used to bind-mount
    ./data/hf_cache over ~/.cache/huggingface to avoid re-downloading weights
    on every container recreate. Once weights are baked into the image at
    /opt/models, that mount would SHADOW the baked copy and reintroduce exactly
    the download it was originally added to prevent. Removing it was part of
    the same change.

9.7 THE CI/CD PIPELINE
--------------------------------------------------------------------------------
BRANCHING: `develop` is the integration branch and deploys automatically to the
dev environment. `main` is production and is promoted MANUALLY via
workflow_dispatch — deliberately, so that production is only ever advanced by a
conscious decision after dev has been exercised. The backend workflow's push
trigger had `main` REMOVED from it specifically to enforce this.

WORKFLOWS:
  * CI (on every push) — backend tests, frontend typecheck and build, and a
    Docker image build (without push). This is the authoritative check; local
    typechecking on the development machine proved unreliable because the
    repository lives on a cloud-synced folder where node_modules reads are
    pathologically slow enough to wedge tsc entirely.
  * DEPLOY BACKEND — builds the image, pushes to GitHub Container Registry
    (GHCR) tagged with the IMMUTABLE COMMIT SHA, then updates the Container
    App. Tagging by sha rather than `latest` is what makes rollback a
    re-pointing operation instead of a rebuild.
  * DEPLOY FRONTEND — builds BOTH environments and publishes one Pages
    artifact.

WHY GHCR RATHER THAN AZURE CONTAINER REGISTRY: GHCR is free for public
repositories and requires no additional Azure resource or credential; the
workflow already authenticates to GitHub. Azure Container Registry's Basic tier
is billed monthly, which violates the $0 target for no functional gain at this
scale.

THE GITHUB PAGES DUAL-ENVIRONMENT CONSTRAINT. Pages publishes exactly ONE
artifact per repository, so both environments must be produced in the same run —
you cannot update one without republishing the other. The workflow therefore
checks out `main` and `develop` separately, builds each with its own
`BASE_PATH`, `NEXT_PUBLIC_API_BASE_URL` and OAuth client id, and assembles them
into a single site directory with dev nested at /dev/. A consequence worth
understanding: a push to develop DOES republish production — but it rebuilds
production from `main`, so live content only changes when main changes.

A SMOKE TEST RUNS AFTER DEPLOY, polling both URLs until each returns 200. A
green deploy step does not prove either URL actually serves — that lesson came
from a "successful" deployment that was serving a completely stale route
surface (9.9).

9.8 BUILD CACHE DESIGN
--------------------------------------------------------------------------------
Baking 2.3GB of weights into the image would be self-defeating if every CI build
re-downloaded them. The Dockerfile is structured so each layer is invalidated
only by its own inputs:

  LAYER                  REBUILDS ONLY WHEN
  -----------------------------------------------------------
  torch (CPU wheel)      its pin changes
  pip install            requirements-api.txt changes
  MODEL DOWNLOAD         docker/fetch_models.py changes
  COPY prompts/          prompts change
  COPY APP/              application code changes  ← the frequent one

The model download lives in its OWN BUILD STAGE depending only on the fetch
script. The obvious placement — after pip install, where sentence-transformers
is already available — would mean a cache miss CASCADES, and every dependency
bump would re-download 2.3GB. Keying the stage to the fetch script alone breaks
that cascade.

THREE FURTHER DETAILS THAT WOULD EACH HAVE SILENTLY BROKEN IT:
  (a) The bge-m3 repository ships PyTorch AND ONNX weights plus README images
      (~5GB together). Only the files the torch backend loads are fetched,
      pinned by commit SHA — which also closes the supply-chain gap of pulling
      whatever a floating tag points at today.
  (b) The weights are baked to /opt/models, NOT ~/.cache/huggingface, because
      docker-compose bind-mounted over the latter (9.6).
  (c) `--mount=type=cache` for pip is NOT exported to the registry cache — it
      only helps local rebuilds. Layer caching is what carries CI.

CI CACHE BACKEND: registry cache on GHCR rather than GitHub Actions cache. The
Actions cache is capped near 10GB per repository with LRU eviction; a 2.3GB
model layer on top of torch under mode=max would thrash it, evict the model
layer, and re-download the weights anyway — defeating the entire exercise.

9.9 DEPLOYMENT VERIFICATION, ROLLBACK, AND INCIDENTS
--------------------------------------------------------------------------------
VERIFICATION DISCIPLINE. "The workflow went green" is not deployment
verification, and this project has the scar tissue to prove it. A workflow
reporting success while the live endpoint served a completely stale route
surface (6 routes instead of 18) is what established the standing rule: after
every deploy, verify the RUNNING SYSTEM, not the pipeline's own opinion of
itself. In practice that means curling the live endpoint, checking
`az containerapp revision list` for BOTH health state and traffic weight, and
for frontend changes, grepping the deployed bundle for the new code — Tailwind
only emits a utility class it actually found in source, so its presence in the
shipped CSS is real evidence rather than an assumption that an edit took effect.

ROLLBACK. Images are tagged by immutable commit sha, so rolling back is
re-pointing the Container App at an older sha — no rebuild, no branch surgery.

INCIDENT 1 — A HEALTHY REVISION AT 0% TRAFFIC. Revision --0000007 held 100% of
traffic while Unhealthy with zero replicas, while an older healthy revision sat
at 0%. Live requests were routed to a revision that could not serve them.
Diagnosed with `az containerapp revision list`; the lesson is that traffic
weight and health are independent properties and both must be checked.

INCIDENT 2 — CRASH-LOOP FROM A MISSING FILE SHARE. New revisions failed with
VolumeMountFailure / "mount error(2): No such file or directory". The Container
App referenced a share that had never been created, because the setup script
swallowed stdout and stderr and printed "(share already exists)" on ANY non-zero
exit. Found in ContainerAppSystemLogs_CL, not application logs — the container
never started, so it had no application logs to produce.

INCIDENT 3 — A TRUNCATED SECRET. The ACS connection string contains `;`;
sourcing the env file without quoting truncated it at the first semicolon, so
OTP email failed at runtime with an opaque error rather than at configuration
time.

10. CONCLUSION, SCALING, AND FUTURE SCOPE
================================================================================

10.1 WHAT WAS ACTUALLY ACHIEVED
--------------------------------------------------------------------------------
A complete, secured, multi-tenant RAG platform running at approximately $0/month
on student credit, with:
  * Three working authentication methods and mandatory login.
  * True multi-document support with isolation enforced at four independent
    layers.
  * A hybrid retrieval pipeline with reranking and neighbour expansion.
  * A three-layer prompt-injection defence built around a structural boundary
    rather than a pattern list.
  * A multi-vendor parser router that escalates to paid OCR only when the free
    tier demonstrably fails.
  * Self-hosted embeddings, making the highest-volume stage structurally free
    and private.
  * Automated CI/CD to two live environments.
  * A real evaluation harness rather than an impression of quality.

10.2 CURRENT LIMITATIONS — STATED PLAINLY
--------------------------------------------------------------------------------
  * maxReplicas is 1, hard-capped by SQLite-on-SMB. This is the primary
    scaling blocker and the reason for the Supabase migration.
  * Cold starts of roughly 20-40 seconds after idle remain, though the
    multi-gigabyte download has been eliminated.
  * OTP emails land in spam (accepted trade-off, section 6.4).
  * INT8 ONNX quantization is implemented but unvalidated on x86.
  * No PII detection yet.

10.3 HOW TO SCALE THIS FURTHER
--------------------------------------------------------------------------------
IMMEDIATE (unblocks horizontal scale):
  1. Complete the Supabase migration, removing the single-writer constraint.
  2. Raise maxReplicas above 1. The application is already stateless apart from
     the SQLite file and the in-process cache — and the cache was deliberately
     designed with Redis as tier 2 precisely so that multiple replicas can
     share it.

MEDIUM TERM:
  4. Move BM25 indexes off the SMB share. Qdrant supports sparse vectors
     natively, which would let hybrid retrieval happen entirely inside Qdrant
     and eliminate the pickle-on-a-network-share pattern altogether — the
     single biggest structural simplification available.
  5. Validate INT8 ONNX embeddings on x86 staging and make it the default,
     cutting model memory ~4x and speeding CPU inference.
  6. Stream answers token-by-token (SSE). Total latency is dominated by
     generation, and streaming makes it FEEL several times faster because text
     starts appearing in about a second. The typing animation currently in the
     UI is a simulation of this over an already-complete response.
  7. Multi-document querying — retrieve across a user's whole corpus rather
     than one document at a time. The payload filter already supports it; it is
     a filter change plus a UI affordance.
  8. PII detection and redaction (section 7.6).

LONGER TERM:
  9. GPU-backed embeddings if volume ever justifies the fixed cost, which would
     collapse ingest time for large documents.
  10. Agentic / multi-hop retrieval for questions requiring several retrieval
      rounds ("compare what section 3 says with section 8") — a genuine
      limitation of single-shot retrieval today.
  11. A caching layer for whole answers to repeated questions, keyed per owner
      and invalidated on re-ingest.
  12. Continuous evaluation in CI with Langfuse or LangSmith, so quality
      regressions fail a pull request.
  13. A custom domain, which would additionally fix email deliverability as a
      side effect (section 6.4).

10.4 CLOSING NOTE
--------------------------------------------------------------------------------
The most valuable outcome of this project is not the feature list — it is that
nearly every significant decision in it was made against a measurement or a
verified constraint rather than an assumption. Semantic chunking was removed
because it was timed. The parallel embedding path was deleted because it was
benchmarked and found slower. The model is gpt-5-mini because four alternatives
were tried and eliminated for documented reasons. CORS middleware ordering was
settled by reproducing both orderings against real Starlette. The grid layout
was fixed by computing that 1016px does not fit in 972px.

Several of the hardest bugs in this project — the query 500, the crash-looping
revision, the blank restored answers, the vanishing citations — presented with
symptoms that pointed confidently at the wrong cause. In every case the fix
came from following the evidence to the root rather than treating the symptom.
That, more than any individual component, is what the codebase is intended to
demonstrate.

11.8 INVESTIGATIVE COMMANDS — HOW FACTS WERE ESTABLISHED
--------------------------------------------------------------------------------
Several conclusions in this document came not from reading but from
interrogating the live system. Recording them because they are reproducible,
and because "the documentation says X" was repeatedly wrong:

  az cognitiveservices model list -l uaenorth
      Revealed that UAE North carries a completely different and current model
      catalog from Central India — the finding that ended the four-attempt
      model search.

  az containerapp revision list -n <app> -g <rg> -o table
      Shows Active, Replicas, TrafficWeight and HealthState together. This is
      what exposed a revision holding 100% of traffic while unhealthy with zero
      replicas.

  Log Analytics: ContainerAppSystemLogs_CL
      Platform-level events. The VolumeMountFailure was only visible here,
      because the container never started and so produced no application logs.

  curl <fqdn>/openapi.json
      Enumerates the routes the LIVE service actually serves — which is how a
      "successful" deploy was proven to be serving a stale 6-route surface.

  docker run --platform linux/amd64 <image> …
      Inspecting the contents of the actually-pushed image, rather than
      trusting that the build did what the Dockerfile says.

  git reflog show / git diff --stat <commit> -- <paths>
      Reconstructed the git history incident and proved no content was lost.

  Reproducing CORS middleware ordering against real Starlette in a scratch
  script, rather than reasoning about it — which is how CORS-last was
  confirmed as the fix.

11.9 A NOTE ON HOW SOURCES WERE USED
--------------------------------------------------------------------------------
Two habits are worth stating explicitly, because they affected the outcome more
than any individual source did.

FIRST: vendor documentation was treated as a starting point, not as ground
truth. Azure's model catalog listed models that could not actually be deployed.
A workflow reported success while serving stale code. A setup script reported
that a file share existed when it did not. In each case the documentation or
the tool was not lying so much as answering a slightly different question than
the one being asked. Every significant claim in this project was verified
against the running system.

SECOND: popularity was not treated as evidence. Semantic chunking is the most
fashionable chunking strategy in the RAG community and it lost, on measurement,
by a factor of five in time for no demonstrated quality gain. Parallelising the
embedding path is an obvious optimisation and it made things slower. Both were
removed. The benchmark, not the blog post, decided.

A.0 THE STARTING POINT — WHAT THE AUDIT FOUND
--------------------------------------------------------------------------------
Before any phase began, an audit of the existing single-document prototype found
problems that made the requested features physically impossible, not merely
harder. These were folded into Phase 1 rather than scheduled separately:

  * `build_hybrid_indices()` called `client.recreate_collection(...)` — every
    /ingest wiped the entire Qdrant collection.
  * `chunk_id` reset to 0..N on every ingest and was used directly as the
    Qdrant point ID — a second document silently overwrote the first.
  * `bm25_data.pkl` was ONE global file holding one BM25 index for the whole
    deployment — no per-document scoping existed at all.
  * /ingest and /query were declared `async def` but called synchronous
    functions directly with no `asyncio.to_thread` — one slow ingest froze
    every other request, including /health.
  * A single ingest re-embedded overlapping chunk text THREE separate times,
    via three independent uncached embedding clients: once inside
    SemanticChunker, once per adjacent chunk pair in the quality gate's overlap
    check (itself double-embedding every interior chunk), and once more in
    build_hybrid_indices.
  * Access control was one shared static string (`SHARED_API_KEY`) compared
    against a header — a deterrent, not authentication.

A.1 THE FOUR ARCHITECTURE DECISIONS TAKEN UP FRONT
--------------------------------------------------------------------------------
Each was an explicit decision with alternatives considered, not a default:

  DECISION 1 — DEFAULT PROVIDER: Azure-billed, not a personal OpenAI account.
    Rationale: the operator should never have their personal API account billed
    by other people's usage.

  DECISION 2 — DOCUMENT PRIVACY: real login, not a client-generated workspace
    id. A workspace id in localStorage is a bookmark, not a security boundary;
    anyone with the id has the documents.

  DECISION 3 — LOGIN SCOPE: MANDATORY across the whole app. No anonymous
    ingest or query path. This is what allowed `SHARED_API_KEY` to be retired
    outright rather than kept alongside.

  DECISION 4 — SEQUENCING: four phased pull requests against `develop`, each
    verified on the staging Container App before merging to `main`.

  AUTH METHOD FEASIBILITY (assessed, all three adopted in Phase 1):
    * GitHub OAuth — free, standard Authorization Code flow.
    * Google OAuth — same pattern, free; a second provider config rather than
      new architecture.
    * Email + password + OTP — the most incremental work, EXCEPT for one real
      constraint: transactional email requires a sender domain the provider
      trusts. Resend and SendGrid only permit emailing yourself until you
      verify a custom domain, which this project does not own (GitHub Pages
      does not give you one). Azure Communication Services Email sidesteps this
      with a pre-verified *.azurecomm.net domain requiring no DNS and no
      purchase. That is why ACS was chosen over the more popular alternatives.

A.10 THE PRODUCTION PROMOTION — WHAT IT ACTUALLY TOOK
--------------------------------------------------------------------------------
Production ran pre-Phase-1 code for the whole of this project's development,
deliberately, while everything was exercised on dev. Promoting it was not a
matter of merging a branch: the environment itself had drifted far enough that
deploying the new image onto it as-configured would have crash-looped it.

WHAT WAS WRONG WITH PRODUCTION BEFORE THE PROMOTION, all found by inspection
rather than by attempting the deploy and watching it fail:

  1. NO `nobrl` MOUNT OPTION. Its volume had NO mountOptions at all. This was
     survivable only because the old code never touched SQLite; the current
     code keeps its auth database on that SMB share, and SQLite's byte-range
     locks cannot be honoured there. This is precisely the fault that
     crash-looped staging.

  2. ONLY EIGHT ENVIRONMENT VARIABLES. Production predated authentication, the
     provider abstraction and the parser router, so it had none of
     JWT_SECRET_KEY, the ACS pair, the GitHub/Google OAuth pairs, or the
     AZURE_OPENAI trio. Without the last of those, /health reports `degraded`
     and the deploy workflow's own smoke test fails the run.

  3. A VECTOR COLLECTION OF THE WRONG DIMENSION — `chunks_collection` at 1536
     (see 5.1).

THE PROMOTION SEQUENCE:
  a. scripts/configure_production.sh — verifies the file share exists (exiting
     non-zero if not), sets five secrets, sets thirteen environment variables,
     and patches the volume to add nobrl.
  b. Every one of those verified by reading back the live configuration.
  c. develop merged into main (27 commits).
  d. CI on main: backend tests, frontend typecheck, Docker build — all green.
     The Docker build took ~10 minutes because main was building the
     model-baking stage for the first time and had no cache to hit.
  e. Backend deploy dispatched with target=production.
  f. Frontend workflow dispatched MANUALLY — see the gotcha below.
  g. Verified against the running system: revision Healthy, 18 routes live on
     /openapi.json, /health reporting ok on chunks_collection_v2, the embedding
     model loading from /opt/models/bge-m3 in ~2 seconds with ZERO
     huggingface.co calls, and the deployed prod bundle containing the new
     frontend code and pointing at the prod backend.

TWO THINGS WORTH RECORDING FROM THE PROMOTION ITSELF:

  * THE FRONTEND WORKFLOW DOES NOT TRIGGER ON A PUSH TO `main`. Its trigger is
    `push: branches: [develop]`. Production is BUILT FROM main, but only when
    the workflow runs — so merging to main updates the source of the prod build
    without rebuilding it. The site kept serving the previous bundle until the
    workflow was dispatched by hand. This is a direct consequence of the
    one-artifact-per-repository constraint in 9.7, and is the kind of thing
    that reads as "the deploy silently didn't work" if you do not know it.

  * THE CONFIGURE SCRIPT FAILED ON ITS FIRST RUN, CORRECTLY. It conflated the
    managed environment's storage REGISTRATION name (`rag-data-storage`) with
    the Azure Files SHARE name it points at (`rag-data`) — two different things
    that are easy to confuse. It exited non-zero and named the problem, which
    is exactly the behaviour its staging predecessor lacked when it reported
    success against a share that did not exist.

     come back, the answer is blank.
  2. Revisiting the URL shows "Backend unavailable" for about a minute, then
     connects on its own.
  3. Answers are slow.

THE SHARED ROOT CAUSE (found during planning, and the reason the plan was
worth writing rather than patching): bge-m3's ~2.3GB weights were never baked
into the API image. They downloaded from HuggingFace on first use into
container-local ephemeral storage, so with minReplicas 0 every scale-to-zero
threw them away and EVERY cold start re-downloaded multiple gigabytes before
the first question could be answered. That single fact explained both symptom 2
and most of symptom 3, and no amount of caching could have papered over it.

DECISIONS TAKEN WITH THE USER DURING THIS PLAN
  * Keep minReplicas 0 and make the wake fast and honest, rather than paying
    ~$50/month for always-warm.
  * Add Upstash serverless Redis (free tier) as a cache tier, caching DOCUMENT
    ARTIFACTS only — not whole answers, not query embeddings.
  * No answer streaming this round.
  * Docker layers must be cached such that only their own inputs invalidate
    them — explicitly requested, and the reason for the dedicated model stage.
